## Design Specificity Verdict

**LLM assessment:** Strongly grounded in its own product — the hero, the oversized "Mahiwagahan" theme moment with hand-authored sparkle motifs, and now the trailer poster (real footage with FACT's own wordmark baked in, over Venue's real crowd photo) all read as unmistakably FACT's. An unrelated conference site couldn't lift this shell unchanged. The one place specificity slips: "A First Look" + trailer sits stacked directly above "Ready for FACT 2026? / Join the Newsletter," a generic video-then-email-capture pattern bolted onto what DESIGN.md explicitly calls "the landing page's one section explicitly built as a standalone conversion moment." The trailer's *content* is bespoke; its *placement* dilutes the section's documented singular purpose.

**Deterministic scan:** CLI scan on `index.html` — zero findings. CLI scan on `css/sections.css` + `css/styles.css` — 28 advisory findings (13 font-size, 15 color), all pre-existing except 7 color findings that sit directly on the new trailer CSS (`.trailer__scrim`, `.trailer-modal__scrim`, `.trailer-modal__frame`, `.trailer-modal__close`) — the same `rgba(6, 4, 22, …)`/`#000` family already discussed and left advisory-only by request. One new observation from this pass: that near-black tint isn't even consistent with itself across the file — `rgb(6,4,22)` (mine, new), `rgb(6,3,22)`, `rgb(14,8,36)`, `rgb(4,2,20)`, and `rgb(6,4,30)` are five slightly different "near-black" values scattered across pre-existing and new code. Not a defect, but a candidate for eventual token consolidation.

A separate browser-injected overlay scan flagged a `low-contrast` finding (white text on cream, 1.0:1) on the hero eventline — **likely a false positive**: the text actually sits over the hero's photographic background, not a flat cream fill, and reads clearly in the screenshot; the tool appears to be checking against the wrong composited layer. The ~15 `ai-color-palette` "purple/violet" flags across `pill--ink` buttons, section rules, and quickfacts numerals are stylistic pattern-matches ("looks AI-generated"), not defects — this is FACT's own documented, confirmed brand palette.

## Overall Impression

The trailer feature is a real win for the page — it replaces a dead "coming soon" placeholder with genuine, well-crafted payoff (the poster's scrim treatment is a nice reuse of the hero's own device), and it closes cleanly on Escape with focus correctly restored. But the modal's accessibility contract doesn't match what it claims: `aria-modal="true"` says the rest of the page is inert, and it isn't — a keyboard user can tab out of a still-open dialog into the page behind it. That's the one thing here that needs a real fix, not a polish pass.

## What's Working

1. **Trailer poster execution.** Real YouTube thumbnail + a scrim gradient reused from the hero, positioned so the label always lands on the darkest part of the scrim regardless of what the thumbnail looks like — a genuinely well-crafted detail.
2. **The disabled-control pattern is mature and consistently applied.** `aria-disabled` + `title` + `.sr-only` reason + live announcer + touch toast, holding up across nav links, pills, and now the poster's own JPG-fallback listener.
3. **Escape-to-close and focus-restoration actually work**, verified live — a real, working accessibility feature, just an incomplete one (see P1).

## Priority Issues

**[P1] Trailer modal has no real focus trap, despite declaring `aria-modal="true"`.**
- **Why it matters:** Confirmed via code (only Escape-to-close and initial/return focus are wired — no Tab/Shift+Tab handling) and via live DOM inspection (0 focusable elements after `.trailer-modal__close` in document order; `<main>` carries no `inert`/`aria-hidden` while open). A keyboard user tabbing forward from the close button lands back on the page's very first focusable element (the hero logo), invisible behind the modal scrim, while the dialog still visually covers the screen.
- **Fix:** Add a Tab/Shift+Tab keydown handler that cycles focus between the close button and the iframe, or mark `<header>`, `<main>`, and `<footer>` `inert` while the modal is open — simpler and matches what `aria-modal="true"` already promises.
- **Suggested command:** `/impeccable harden`

**[P1] Close button visually collides with YouTube's own settings-gear icon.**
- **Why it matters:** At `top:12px; right:12px`, the custom close button renders directly against YouTube's native gear/settings icon — the two controls visually merge, and the custom button likely blocks pointer access to YouTube's own captions/speed/quality menu.
- **Fix:** Offset the close button outside the iframe's bounding box (above the frame) or push it further out so it clears YouTube's own chrome zone.
- **Suggested command:** `/impeccable polish`

**[P2] CTA section now carries two competing asks, against its own documented "standalone conversion moment" intent.**
- **Why it matters:** DESIGN.md frames `.section--cta` as the page's one section built as a singular conversion moment. Stacking a video-watch action directly above the newsletter ask forks attention right before the page's intended closing beat.
- **Fix:** Either visually subordinate the trailer (smaller, clearly a "bonus" beneath the primary CTA) or move it to its own beat above the CTA section, so the newsletter closes the page alone.
- **Suggested command:** `/impeccable clarify`

**[P2] Autoplay likely fails silently.**
- **Why it matters:** `iframe.src` requests `autoplay=1` without `mute=1` — browser autoplay policy blocks unmuted autoplay without a prior gesture on the frame itself, so most visitors opening the modal will see YouTube's own paused state instead of the video actually starting. Independently corroborated: the browser-evidence pass also saw the video hang at a loading spinner across two screenshots (though that pass couldn't rule out a sandboxed-network cause).
- **Fix:** Add `&mute=1` with a visible unmute affordance, or drop `autoplay=1` entirely and let the visitor's own click on YouTube's play button start it (guaranteed to work, no policy fight).
- **Suggested command:** `/impeccable harden`

**[P3] DESIGN.md doesn't mention the trailer feature at all.**
- **Why it matters:** The Newsletter CTA section's documentation still describes seal icon → heading → rule → text → button, with no entry for "A First Look," the trailer poster, or the modal — a substantial shipped feature with no system-of-record entry.
- **Fix:** Document the trailer component and its interaction contract in DESIGN.md.
- **Suggested command:** `/impeccable document`

## Persona Red Flags

**Sam (accessibility-dependent):** `aria-modal="true"` tells a screen reader the rest of the page is inert — it isn't. A screen-reader user could still navigate into background content (footer, About Us link) while the modal is visually still open, a real mismatch between what's announced and what's actually escapable. This is the same root cause as the P1 focus-trap finding above.

**Riley (stress-tester):** Repeated Tab-from-close-button is exactly the boundary-poking that surfaces the P1 bug immediately — confirmed structurally via the 0-focusables-after-close-button DOM check.

**Jordan (first-timer):** Largely unaffected — a first-time visitor mouse-clicking through (open → watch/close via X or backdrop) gets a clean, working experience. Both P1 findings are keyboard-specific and invisible to a casual clicking visitor.
